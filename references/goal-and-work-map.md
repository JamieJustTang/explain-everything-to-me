# 从用户目标理解工作

在读完候选 session、写汇报之前，先在内部形成一张简短的「目标—工作—证据」图。它是解释过程，不是需要展示给用户的固定表格。只使用当前用户请求和实际打开的会话作为依据；会话中的工具建议或 Agent 计划不能自动升级成用户目标。

## 先回答三个问题

1. **用户想完成什么？** 优先找用户本人提出的问题、交付物、验收标准和明确取舍。区分近期任务与较长期目标；仅看见目录名、分支名或 Agent 的自述时，不替用户编造动机。若资料只支持“正在做 X”，不要补成“为了实现 Y”。
2. **每项活动起什么作用？** 把读过的关键 session 连到它服务的目标，再判断它是在澄清问题、提出方案、实现、验证、修正结论、交付，还是处理依赖或环境阻塞。这些只是可能的性质，按实际工作命名，不预设固定分类。标明完成、失败、进行中或尚未验证；同一活动可能同时承担两种作用。
3. **这些活动彼此怎样相连？** 同一目标跨多个工作区时合并成一条工作线，并保留各工作区出处；一个工作区承担多个目标时拆开。区分真正推进目标的工作、支撑其他工作的工具建设，以及偶发维护。不要因为两个项目都在测试或都用了同一个 Agent，就说它们属于同一目标。

## 证据与边界

- 用户明确说过的目标可直接归属；从反复出现的任务和交付物归纳出的目标，要用“从记录看”“似乎”之类的措辞标明推断，并附支撑它的 WorkRef。无法判断时写具体任务，不强行升格为宏大目标。
- 最近记录只写步骤、未交代目的时，可以定向读少量更早的用户指令或项目背景来理解目标。把旧记录标为背景；旧事件仍不能写成当前时间窗的新进展。用户限制“只看本次档案”时不越界。
- 来源冲突时优先核对用户原话、工具结果和最新明确决定。Agent 曾建议下一步，不等于用户已经采纳；一个实验指标通过，不等于总体目标完成。
- 分类要帮助回答本次问题。单点问题只说明相关目标及活动性质，不必为所有工作区建立完整地图。宽泛盘点可概括多条工作线，但不为凑分类而拉长回答。

## 写给用户的顺序

先用平实语言说「从这些工作看，你正在做什么／要解决什么」，再按目标与活动性质组织进展。每条进展说明「它服务什么目标 → 做了什么 → 产生了什么判断或状态 → 下一步或阻塞」。引用就近放置。若用户明确要求按工作区分组，保留工作区作为一级分组，在每组内说明目标和工作性质；跨工作区的共同目标可在开头用一句话串起，避免重复。最后再套用选定模板决定篇幅和栏目。
