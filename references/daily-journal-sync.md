# 可选组件：日拱一卒每日日志

仅当**当前安装副本**存在 `components/daily-journal/component.json`，且用户显式调用本 Skill 进行工作解释或要求记日志时，执行本流程。查看语言规则、安装设置等纯配置请求不触发采集。源码仓库有组件目录不等于宿主已安装。页面打开也不触发采集；每日定时运行需要用户另行设置。

## 每次调用的边界

1. 记录调用时刻和用户本地日期。日志的“今天”固定为**本地当天 00:00 到本次调用时刻**，即使本次解释的问题只问某一项目、只问“自上次调用后”或只查另一个日期。日志要保留当天前面几次调用留下的小进展。用户若明确限制资料来源、工作区或禁止记录，遵守该限制；禁止记录时完全跳过写入。
2. 用[检索手册](retrieval.md)的 `archive:agent` 加时间边界查可访问的本机各工作区、各 Agent 记录。必要时用宿主已有的只读会话工具补足当前尚未归档的对话。按工作区和 session 去重，先找当天活动，再打开相关原文；长会话只读与当天变化有关的必要段落。不能只依赖本次主问题的命中，也不能把搜索摘要直接写进日志。归档范围不完整时保留实际覆盖说明，不声称“读完所有 Agent 对话”。不要为了日志擅自扩大用户授予的来源范围、连接远端或复制会话。
3. 从用户的目标和当天原文中提取小而可核对的变化：推进、留下的产物、发现的反例或问题、确实发生的交流。按变化实际发生的本地日期归属，跨午夜的 session 不整体归到结束日。每条自动条目必须有真实 WorkRef；没有可靠证据就不写。核实产物的真实绝对路径或可访问链接及名称，不凭 Agent 的计划填“已完成”。不要把密钥、长篇转录或敏感原文写进日志。

## 写入与复核

从**安装副本**运行 `python3 components/daily-journal/journal.py`。默认数据只在用户目录 `~/.explain-everything-to-me/daily-journal/data.json`；不得写入仓库示例。先 `show` 读取当天已有条目和用户手写记录。以 `import --input FILE` 或标准输入提交 `{"events":[...]}`；事件格式见[组件说明](../components/daily-journal/DESIGN.md)。每个 Agent 事件的 `key` 使用 `本地日期:真实工作区:稳定事项`，重复调用更新同一事项；不要用随机时间戳。空事件数组也可记录本次检查。已删除的键不得重建，手动修改的字段不得覆盖，`shared` 只能由用户标记。

导入后再 `show`，用 `key` 找生成的条目 ID。只有当天至少一条可靠条目时才 `compose --input FILE`。撰写短篇连贯的日志：说明今天在做什么、为什么、推进中的转折、留下的对象与尚未解决的问题。正文引用真实产物时，必须在相关句子中写 `[[artifact:条目ID]]`，并把该 ID 放入所属段落的 `entry_ids`；不要另列重复的产物清单。`coverage_note` 简述已查时间、来源和缺口。READY TO SHARE 写成给用户的私人建议信：根据产物成熟度建议是否展示、给谁看、带什么问题；若当天有产物，信中至少引用一个真实产物；若尚无产物，可引用发现或进展条目，诚实说明还差什么可见对象。不能声称已经发布、分享或联系他人。完整格式与校验见[组件说明](../components/daily-journal/DESIGN.md)。

重复调用时更新当天摘要，连同用户手写记录一起判断，但手写内容要标明为用户记录，不能变成 Agent 验证事实。若用户仅要求补记另一天，可按指定日期处理，不把旧事件写成今天。采集失败、来源缺失或摘要校验失败不阻断主回答；简短说明实际完成到哪步，以及是否仅保存了条目。不要静默把上次日志说成已更新。

只有用户要查看页面时才运行 `python3 components/daily-journal/journal.py serve`，访问 `http://127.0.0.1:8767/`。服务只监听本机。安装时不导入 `example.json`，不启动服务，不创建自动任务。
